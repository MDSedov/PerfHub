# Правила работы с PerfHub

## Обязательный процесс изменений

Все последующие функциональные и архитектурные изменения, включая рефакторинг без изменения поведения, выполнять **только через OpenSpec** по порядку:

1. **Explore** — исследовать реализацию, действующие требования, тесты и влияние изменения; проверить состояние репозитория.
2. **Proposal** — создать небольшое отдельное изменение: проблема, цель, границы, результат и исключения.
3. **Specs** — сформировать проверяемые требования и сценарии; явно выделить изменение поведения. Для чистого рефакторинга без изменения требований использовать поддержанный `skip_specs: true` в `.openspec.yaml`, не создавать искусственные delta specs. Сохранение поведения проверять в design/tasks и тестах.
4. **Design** — при необходимости описать решение, альтернативы и риски в рамках утверждённого стека.
5. **Tasks** — разбить работу на проверяемые пункты, связанные с требованиями или необходимыми техническими действиями.
6. **Review** — выполнить `openspec validate <change-name> --strict`, представить proposal/specs/design/tasks владельцу и получить согласование. **До согласования реализация запрещена.** Подготовка артефактов и статус CLI «ready/done» согласованием не являются.
7. **Apply** — только по отдельному запросу и только утверждённый объём. Не добавлять функциональность вне требований. При существенном изменении требований сначала актуализировать OpenSpec и повторно согласовать затронутую часть.
8. **Verify** — проверить соответствие требованиям/сценариям, уместные тесты, отсутствие регрессий и непредусмотренных изменений, стек и границы diff.
9. **Archive** — только после завершения и проверки, штатными средствами OpenSpec с обновлением основных specs и по отдельной команде владельца. Не обходить lifecycle прямой записью baseline в `openspec/specs/`.
10. **Git** — commit, push, merge и deployment только по отдельной команде владельца.

Запрос на аудит, baseline или предложение разрешает подготовку материалов, но не реализацию, исправление дефектов, архивирование или Git-операции. Следовать графу зависимостей артефактов установленной схемы, не подменяя обязательный review их наличием.

Небольшие независимые изменения предпочтительнее общего рефакторинга. Указывать зависимости, исключения из области работ, риски, проверки совместимости и способ отката. Документацию и содержимое OpenSpec-артефактов писать по-русски; обязательные машинные заголовки OpenSpec, идентификаторы и имена файлов сохранять.

Перед работой проверять ветку, `git status`, действующие инструкции и `openspec context --json`. Не перезаписывать и не откатывать чужие изменения. Существующее изменение OpenSpec актуализировать осознанно, не создавать конкурирующие планы с тем же именем. Исправления документации и планов не требуют отдельного изменения ради самих себя.

## Ограничения рефакторинга

- Утверждённый стек: Java 17, Spring Boot / Spring MVC, Thymeleaf, Bootstrap 5, Vanilla JavaScript, Maven и существующий механизм хранения данных. Версии определяет текущий `pom.xml`. Любое изменение стека, языка, зависимостей, их версий или сборщиков требует отдельного OpenSpec-предложения с обоснованием и **явного согласования владельца**. Не вводить React, Vue, Angular, TypeScript или frontend-сборщики в рамках обычного рефакторинга.
- Сохранять URL, методы HTTP, JSON-контракты, статусы и сообщения ошибок, авторизацию и роли, данные и схему БД, протоколы интеграций и последовательность внешних операций. Намеренное изменение поведения оформлять отдельно от рефакторинга.
- Не удалять предположительно неиспользуемый код по одному отсутствию текстовых ссылок: учитывать маршрутизацию Spring, Thymeleaf, динамические DOM-селекторы, загрузку ресурсов и внешних потребителей API.
- Не выводить и не записывать в документацию секреты, хеши паролей, содержимое пользовательской БД, экспорт подключений и реальные заголовки авторизации. Для диагностики использовать обезличенные данные.
- Не выполнять commit, push, merge, публикацию или deployment без отдельной команды владельца.

## Требования и доказательства

Разделять A (подтверждённый AS-IS), B (неутверждённый TO-BE), C (дефект/риск), D (неподтверждённое предположение). Для каждой существенной формулировки указывать основание: код, существующий тест, проверка работающего приложения или отсутствие подтверждения. Не считать наличие метода доказательством сквозной работоспособности, mock-тест — проверкой корпоративного подключения, валидацию OpenSpec — функциональным тестом.

Требования получают стабильные ID `PH-<область>-NNN`, сценарии — суффиксы `-SNN`; ID не переиспользовать. Поддерживать `docs/requirements/traceability.md` и `gaps-and-decisions.md` при изменении требования. Дефект не становится нормой: ожидаемое исправленное поведение согласовывается отдельно. Противоречия specs и кода фиксировать, не исправлять молча.

`baseline-existing-perfhub` официально согласован владельцем 12.10.2026 как AS-IS. Его 8 спецификаций, 41 требование и 93 сценария перенесены штатным архивированием в `openspec/specs/`; основные specs — база дальнейших изменений. Изменения НФТ (статусы, интервалы, источники порогов), включая configure-test-type-evaluation-windows, отложены; спорные вопросы остаются в реестре. Существующее `refactor-shared-ui-layout` не считается автоматически утверждённым; перед его применением сверить границы с принятым baseline.

## Соглашения о коде

- Сохранять слои `controller → service → repository/client`. Контроллеры отвечают за HTTP и DTO, сервисы — за сценарий, репозитории — за SQL, клиенты — за транспорт интеграций. Чистое форматирование и разбор выносить в предметные компоненты, когда это обосновано задачей. Не переносить все пакеты разом.
- Использовать существующие Java records для DTO, constructor injection, `final` для зависимостей, четыре пробела, явные импорты и существующий стиль изменяемого файла. Не делать массовое форматирование попутно.
- Валидация входа — на границе HTTP; предметные ограничения — в сервисе. Общий внутренний DTO ошибки допустим только с сохранением существующего внешнего представления. Согласовать область `ControllerAdvice` до объединения обработчиков.
- Логировать через SLF4J с параметрами, указывать операцию и безопасные идентификаторы. Не логировать сырые заголовки, тела запросов интеграций, секреты и конфигурационные экспорты. Новая политика маскирования существующих логов — отдельное изменение с проверкой отсутствия секретов.
- SQL и транзакционные границы сохранять при механическом переносе. Не включать внешний HTTP в новые транзакции и не менять retry, timeout, кеширование и область пользовательских настроек без отдельного плана.
- Повторяемую серверную разметку размещать в `templates/fragments/`. Сохранять DOM ID, `name`, `data-*`, ARIA-связи, порядок скриптов и активные пункты меню. Небольшой синхронный скрипт восстановления sidebar до первого отображения допустим в общем head.
- Цель для JS — отдельные файлы `static/js/pages/` и `static/js/shared/` с явными зависимостями. Переход к нативным ES-модулям проводить отдельным изменением после проверки порядка выполнения; не менять тип скрипта при извлечении общей разметки.
- Цель для CSS — именованные переменные `--perfhub-*`, общие компоненты и ограниченные страницей стили. Сохранять фирменные цвета, логотипы и фактический каскад. Дублирование не удалять без проверки влияния media queries и специфичности.

## Проверки

Для каждого изменения заранее определить регрессионную матрицу. Для изменений кода запускать относящиеся тесты и `mvn test` в подтверждённо безопасном окружении; для чистой документации проверять источники, ссылки, согласованность и границы diff. Проверять OpenSpec в строгом режиме. Если безопасность тестов не подтверждена, не запускать их, зафиксировать ограничение. Не скрывать существующие ошибки и не ослаблять проверки ради зелёного результата. Указывать JDK и ограничения проверки: Java 21 с `release=17` не заменяет прогон на JDK 17.

`PerfHubApplicationTests` использует внешнюю конфигурацию с файловой H2. До появления изолированного тестового профиля запускать тесты в временной копии `pom.xml`, `src/` и `config/application.properties`, предварительно проверив относительный путь H2. Не копировать пользовательские БД, кеш графиков и секретные экспорты. Не запускать приложение на пользовательской БД для визуальной проверки. Для страниц использовать тестовые данные и подмену внешних интеграций.

При изменениях UI проверять рендеринг Thymeleaf и браузерные сценарии, роли, активную навигацию, sidebar при 992/993 px, формы, модальные окна, уведомления и отсутствие новых сетевых запросов. Зафиксировать известные ошибки отдельно. Не считать успешный `mvn test` доказательством визуальной совместимости.
