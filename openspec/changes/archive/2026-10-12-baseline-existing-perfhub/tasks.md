# Задачи завершения документирующего baseline

Baseline официально согласован владельцем 12.10.2026. Ниже отмечены выполненные документирующие задачи; основания по каждому пункту находятся в [протоколе review](../../../../docs/requirements/baseline-review.md). Сверка 8/41/93, источников, ссылок и строгая валидация завершены, результат представлен владельцу перед исполнением его команды archive. Изменения приложения не выполнялись.

## 1. Review кандидатных требований

- [x] 1.1 Рассмотреть proposal/design и восемь specs вместе с владельцем; зафиксировать по каждому PH-ID принятие, редакционное уточнение либо исключение. Проверка: существует явный результат review, без выдуманной даты/согласования; неподтверждённые требования не помечены утверждёнными.
- [x] 1.2 Рассмотреть Q-01…Q-10 в docs/requirements/gaps-and-decisions.md; для каждого зафиксировать решение или явное отложенное решение с границей исключения из baseline. Проверка: ни legacy-дефекты, ни спорные no-data/секреты/merge не стали нормой по умолчанию; исправления вынесены в отдельные предложения.
- [x] 1.3 Сверить принятую навигацию PH-AUTH-006 и UI-сценарии с областью уже подготовленного refactor-shared-ui-layout. Проверка: нет противоречий принятым требованиям и автоматического разрешения на применение старого change; необходимость его отдельного уточнения записана.

## 2. Редакционное завершение после согласования

- [x] 2.1 По отдельному запросу актуализировать кандидатные формулировки только в согласованном объёме; сохранить ID и обновить traceability для каждого затронутого требования. Проверка: все принятые требования имеют сценарии и точные источники, отсутствуют переиспользованные ID и дубли.
- [x] 2.2 Сверить карты API/UI/интеграций/данных с актуальным исходным срезом и уточнить документацию только при обнаруженном изменении фактов. Проверка: каждый объявленный HTTP-handler и шаблон учтён, уровни «код/тест/приложение» не повышены без доказательства; пользовательские данные не открывались.
- [x] 2.3 Зафиксировать состояние baseline после review в документации и проверить AGENTS/config на согласованность SDD, технологических ограничений и исключений. Проверка: статус принятия соответствует фактическому решению владельца; требования к другому стеку/версиям не появились без отдельного предложения.

## 3. Общая верификация перед завершением

- [x] 3.1 Повторить `openspec validate baseline-existing-perfhub --strict`, проверить число specs/требований/сценариев и ссылки матрицы. Проверка: нет ошибок/предупреждений строгой валидации, каждой строке матрицы соответствует уникальный PH-ID и сценарии.
- [x] 3.2 Проверить `git status`, diff и контрольные суммы относительно начала соответствующего прохода. Проверка: приложение, SQL, зависимости, данные и чужие changes сохранены; при чисто редакционном завершении Maven/корпоративные вызовы не нужны. Новые функциональные доказательства указывать только при фактической безопасной проверке.
- [x] 3.3 Представить владельцу результат review и верификации с оставшимися исключениями и отдельными следующими изменениями. Проверка: принятое содержимое, пробелы покрытия и отсутствие реализации явно отражены; ни архивирование, ни Git не выполнены автоматически.

## Workflow follow-up

- Только после review, завершения перечисленных задач и проверки, по отдельной команде владельца штатно архивировать baseline с обновлением основных specs; проверить перенесённые требования и ссылки. На проходе завершения владелец дал отдельную явную команду на архивирование; выполнить после всех проверок.
- Исправления безопасности/изолирование тестов, устранение legacy-расхождений и рефакторинг оформлять отдельными небольшими OpenSpec changes в порядке, описанном в реестре.
- Commit, push, merge и deployment возможны только по отдельной команде владельца.
