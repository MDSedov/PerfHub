# Проектирование документирующего baseline

## Context

Мотивация — [proposal.md](proposal.md). Источник исследования: `main`, `f3498db`; основные `openspec/specs/` пусты, `refactor-shared-ui-layout` уже подготовлен и сохранён без правок. Продукт содержит MVC/Thymeleaf, JDBC/H2 и шесть интеграций; описание реализации вынесено в [архитектуру](../../../../docs/architecture.md). Здесь проектируется управление требованиями, а не новая архитектура приложения.

## Goals / Non-Goals

**Goals:** связать каждое кандидатное требование со сценариями и доказательствами; явно отделить нормативный кандидат от факта кода, риска и нерешённой политики; обеспечить согласование и штатное последующее формирование основных спецификаций.

**Non-Goals:** перенос классов/разметки, изменение UI, API, SQL, данных, авторизации, кеширования, retry, зависимостей; исправление дефектов; проверка корпоративной среды; утверждение требований от имени владельца. Срез ограничен доступными исходниками и существующими тестами.

## Decisions

1. **Восемь возможностей, а не спецификация на класс.** Пользователи/профиль/доступ объединены; типы находятся рядом с тестами; формирование и публикация отчёта объединены как пользовательский результат. Числовая проверка требований отделена от текстового анализа GigaChat. Альтернатива с десятками CRUD-спецификаций создаёт повторы, единый файл для всего приложения затрудняет review.
2. **Технические факты — в docs, ожидаемое поведение — в specs.** Карты маршрутов и данных описывают также legacy и ошибки. Delta specs содержат только обоснованные кандидаты, без утверждения сомнительного поведения. Автоматический перенос любого if/exception в SHALL закрепил бы дефекты. Спорные no-data/credential/legacy/merge политики оставлены вне нормативной части, перечислены в реестре решений и не блокируют подготовку кандидата.
3. **Постоянные ID `PH-AUTH/TEST/MET/GRAF/STAND/NFR/REP/CFG-NNN`.** Сценарий имеет производный `-SNN`. При удалении требование помечается выведенным из использования, ID не назначается другому смыслу. Матрица хранит ссылку на requirement, сценарии, маршруты, точные файлы и тестовые методы. Тест указывается как частичное подтверждение, если он не покрывает весь HTTP/браузерный путь. Альтернатива «все требования покрыты, потому что Maven зелёный» недопустима.
4. **Разделение статусов.** A/B/C/D описывают тип знания; «код / автоматический тест / работающее приложение / не подтверждено» — независимую ось доказательств. Все SHALL в этом изменении — кандидаты B на основе A. `openspec status` подтверждает наличие артефактов, не review и не корректность продукта.
5. **Безопасная верификация документации.** Сверяются все контроллеры, DTO и 18 шаблонов; локальные ссылки, ID и методы тестов; контрольные суммы источников и старых артефактов; `openspec validate ... --strict`. Предыдущий изолированный Maven-прогон отмечен как историческое доказательство того же исходного среза, не запускается повторно из пользовательского каталога. Браузерные и интеграционные доказательства отсутствуют и не симулируются.
6. **SDD с review.** AGENTS/config фиксируют Explore→Proposal→Specs→Design→Tasks→Review→Apply→Verify→Archive→Git. Для чистого рефакторинга без изменения требований применим `skip_specs: true`; для данного baseline spec delta необходима. Прежний layout change не переделывается задним числом. Стек остаётся Java 17, Spring Boot/MVC, Thymeleaf, Bootstrap 5, Vanilla JavaScript, Maven и существующее хранение. Изменение стека/версий/зависимостей — отдельное предложение с явным согласованием.

## Risks / Trade-offs

- [Восстановление требований по коду может узаконить дефект] → ограниченные входные условия сценариев; отдельный реестр Q-01…Q-10; утверждение владельцем перед нормативным применением.
- [Сервисные тесты не проверяют HTTP и UI] → в матрице прямо указаны частичные доказательства; отдельное будущее покрытие MVC/Thymeleaf после изоляции тестов.
- [Документы расходятся со временем] → изменять specs и матрицу в том же OpenSpec change, фиксировать противоречия до правок кода; не переиспользовать ID.
- [Открытые legacy API потеряются из карты] → все 87 handler документированы; исключённые из кандидатов возможности перечислены с причиной и решением владельца.
- [Два подготовленных change затрагивают UI] → baseline описывает пользовательские переходы и операции; layout change — совместимость разметки. Перед apply сверить оба плана после review; текущие файлы layout не менять.
- [Документация раскроет секреты] → только имена параметров и механизмы; никакого копирования конфигурационных значений, БД, экспортов или реальных auth headers.

## Migration Plan

Миграции данных, rollout приложения и deployment не требуются. Сейчас создаются только кандидатные документы и правила процесса. Владелец рассматривает требования, исключения и вопросы; дальнейшее согласование фиксируется отдельным действием, без заполнения выдуманной даты/подписи.

После согласования отдельным запросом выполнить задачи завершения baseline, повторить проверку среза и артефактов. Архивирование и синхронизация основных specs — только штатным механизмом OpenSpec, после завершения/верификации и отдельной команды владельца. Сейчас `openspec/specs/` не заполняется.

Откат документирующего изменения: отменить только добавленные baseline-документы и правки правил после проверки чужих изменений; не трогать исходники, существующий аудит или layout change. Приложению откат не требуется, поскольку оно не меняется.

Вопросы владельцу находятся в [gaps-and-decisions.md](../../../../docs/requirements/gaps-and-decisions.md). Это явно исключённые спорные области будущего согласования, а не скрытые технические решения для реализации текущего документирующего изменения. Задачи review ниже проверяют границу и не разрешают исправлять приложение.
