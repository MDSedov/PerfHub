### C/D — установленные ограничения и неизвестное

Существенная диагностическая информация теряется между HTTP-ошибкой и уведомлением. Корпоративный ответ не получен: права, selector, URL datasource и конкретная причина остаются D. Нельзя назначать причиной HTTP 400/403, исправлять кавычки selector или менять источник по имеющимся фото. Общий журнал может содержать секреты Confluence (G-01), поэтому его копирование в отчёт запрещено; чужой security-план не изменяется.

## Goals / Non-Goals

**Goals:** один небольшой локальный отчёт после обычного действия пользователя; различение этапа/HTTP-кода/категории; предсказуемый путь; сохранность текущего каталога при любом исходе диагностики.

**Non-Goals:** отдельная страница, кнопка/API скачивания, постоянная история отчётов, новый logging backend, новые настройки подключения, изменение формул/метаданных/протокола API либо общего логирования. Нужен design, поскольку задействованы клиент, сервис и запись безопасного артефакта.

## Decisions

### 1. Отдельные безопасные метаданные ошибки

В catalog-методах клиента ввести внутренний диагностический подтип GrafanaClientException с фиксированным этапом, категорией и nullable числовым HTTP-кодом. RestClientResponseException даёт фактический код; транспортный сбой не получает вымышленного статуса. При пустом/неверном JSON и некорректном data после HTTP 200 сохранять код 200 и категорию INVALID_RESPONSE. Для этого helper сохраняет статус успешного HTTP-ответа до проверки тела/преобразования. Классифицировать ошибку десериализации отдельно от отсутствия HTTP-ответа.

Cause допускается сохранить внутри исключения для совместимости, но ни cause, ни его сообщение/класс/stack trace не сериализовать в отчёт или новые логи. Остальные методы GrafanaClient и класс прежнего исключения не перерабатывать.

Этапы ограничить перечислением: CATALOG_INITIALIZE, DASHBOARD_SEARCH, DASHBOARD_LOAD, DASHBOARD_PARSE, DEPLOYMENT_CONTEXT, DEPLOYMENT_VALUES, CONTEXT_CHECK, SNAPSHOT_PUBLISH. Категории: HTTP_ERROR, TRANSPORT_ERROR, INVALID_RESPONSE, INVALID_CONTEXT, UNSUPPORTED_METADATA, CONTEXT_CHANGED, LOCAL_STORAGE_ERROR, UNKNOWN. Для типовых причин использовать заранее заданное русское пояснение. Не вычислять категорию по сырому тексту исключения.

Сервис отмечает этап перед соответствующей операцией и учитывает также ветки sameContext=false и save=false. Ошибки до цикла, при чтении snapshot и в существующем fallback ConnectionTestService также получают безопасный итог; если определить пользователя невозможно, чужой или глобальный файл не перезаписывается, выдаётся предупреждение о невозможности сохранить отчёт. Новый отчёт создаётся только в уже существующей попытке refresh после успешного health.

Альтернатива — логировать ex/cause целиком. Отклонена: может раскрыть URI, тело upstream и секрет. Повторять запрос для диагностики также не требуется.

### 2. Разрешённая структура отчёта

Использовать небольшой record результата проверки и record записи ошибки. Только эти типы передаются компоненту записи, Throwable/JsonNode/HTTP request/response — никогда. Разрешённые поля: версия формата, сгенерированный UUID проверки, времена начала/завершения UTC, итог каталога, числовые счётчики, этап/категория, nullable HTTP-код, фиксированное пояснение и SHA-256-ключ dashboard UID. Сам UID, title, datasource, namespace, deployment, query и адреса не записываются. Ключ применяется только для связи ошибок одного дашборда, не является доказательством анонимности исходного UID.

Формат — читаемый UTF-8 текст с русскими подписями и машинными этапами/кодами. Пример только на синтетических значениях: `Этап: DEPLOYMENT_VALUES; HTTP: 403; Категория: HTTP_ERROR`. Общий журнал не читается. Новые сообщения SLF4J получают тот же разрешённый набор полей через параметры, без последнего аргумента Throwable.

Счётчики охватывают всю попытку, список ограничен первыми 100 ошибками; число пропущенных записей указано явно. Текст ограничен 128 КиБ; ограничение применяется без разрыва записи и с сохранением заголовка/итога. Счётчики отдельно различают отказы dashboard и глобальный отказ, а не называют ошибку search неудачным dashboard.

### 3. Локальный файл последней проверки

Новый компонент записи отчёта использует стандартный Java NIO, не добавляет зависимости и не настраивает глобальные logback/root logger. Это сохранение диагностического документа; сообщения о выполнении остаются через SLF4J. Путь — `logs/grafana-catalog-diagnostics-user-<id>.txt`, где id берётся из существующего CurrentUserProvider, 0 используется только для подтверждённого глобального контекста. Идентификатор пользователя не поступает из HTTP-параметра имени файла.

Каталог создаётся при записи. Полный отчёт сначала сохраняется во временный файл в том же каталоге, затем заменяет прежний через atomic move; при неподдержанной атомарной операции используется короткая синхронизированная замена готового файла. Временные файлы удаляются после попытки. Записи одного процесса синхронизируются на финальной публикации; внешние HTTP-вызовы под блокировку не попадают. При параллельных проверках сохраняется один полный результат, с собственным ID; порядок начала проверок не обещает порядок завершения. Совместная запись нескольких JVM в один рабочий каталог не входит в область.

Остаётся один файл на пользователя, без истории и роста при повторении. Ошибка создания/записи/замены не меняет success, status, snapshots или транзакции. Возвращается только заранее заданное сообщение об ошибке сохранения и безопасное резюме в консоль. Сохранившийся прежний файл явно не называется новым результатом. Пользовательский путь/текст IOException не показывается.

Альтернатива — включить общий файловый лог или dedicated appender в logback-spring.xml. Отклонена: общий лог небезопасен, а настройка appenders меняет запуск и конфигурацию всех журналов ради одного отчёта. Новый HTTP endpoint скачивания потребовал бы отдельного контракта доступа и здесь не нужен.

### 4. Прежняя форма уведомления

Сохранить DTO и HTTP-схему. К прежнему catalog.message добавить ID проверки и относительный путь; для IDE запуски обычно используют корень проекта, но это не гарантируется — README объясняет рабочий каталог процесса. При несохранённом отчёте добавить явное предупреждение. Верхнеуровневые service/success/message и catalog.status/updatedAt сохраняются. Глобальный fallback должен вызывать тот же компонент диагностики, а не собирать вторую политику текста.

HTML/CSS/JS, DOM ID, порядок скриптов и стили не изменяются. Тест рендера/браузера проверяет, что существующее уведомление и title действительно показывают путь или ошибку записи без HTML-интерпретации. Импорт настроек G-22 по-прежнему может скрыть catalog.message; основной пользовательский путь — явная проверка на странице подключений.

## Risks / Trade-offs

- Отчёт не содержит сырой upstream error → точная причина может потребовать следующего узкого исследования; этап/код существенно сужают поиск, но не объявляются готовым исправлением.
- Непонятный рабочий каталог → относительный путь показан в уведомлении; в README отдельный пример запуска из каталога проекта.
- Нет прав на logs/ошибка диска → не ломать проверку, явно сообщать отказ записи; тестировать без изменения прав реальных каталогов.
- Последняя параллельная проверка заменяет файл → UUID в уведомлении/файле позволяет сопоставить результат; отдельные файлы пользователей не смешиваются. Владелец может повторить одну проверку перед отправкой.
- Корпоративные подключения не проверяются локально → использовать mock HTTP и синтетический локальный источник; не копировать пользовательскую БД/экспорты/старые логи.

3. После Verify использовать уже данное владельцем разрешение commit/push только относящегося diff; чужие untracked-файлы исключить. Archive и обновление основных specs требуют отдельной команды; без неё их не выполнять. Merge/deployment не выполнять.
4. Откат — вернуть код диагностики и документацию к предыдущей версии. Файлы отчёта не используются приложением как вход и могут быть удалены владельцем; БД, snapshots и PNG не преобразуются.
